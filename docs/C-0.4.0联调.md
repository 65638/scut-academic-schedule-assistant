## 新任务只读恢复

另起真实 WorkBuddy 专家任务，正常加载 0.4.0。输入只提供两条合成业务编号与预期，重新发现个人空间、根节点和唯一日程表，核对归属、schema 后读取新的在线 CSV；未读取旧任务 CSV、回读或平台 ID 缓存。客户端发现调用的实际 trace 与本轮原始响应一致。

随包 snapshot 恢复两项，再按业务编号分别 query 得到唯一平台记录，逐条原生 get_record 回读。两个回读文件与主任务最终回读逐字节相同；两项均为 18:30、B202，保留新对象、新材料、根来源、首次收录时间和一条四字段更正历史。昨日 0.3.1 两条示例也保留原状态及 history=1/0。

恢复前后在线 CSV 均为 13642 字节、5 条记录，逐字节一致；全程云端零写。独立审查核对发现链、15 字段 schema、query、单条回读、快照与前后 CSV，99 项原始证据断言全部通过。恢复任务使用 DeepSeek-V4.1-Flash，消耗 2.81 积分；与前述 U1/U4 主任务合计 8.34 积分，不代表 B/D 全功能体验成本。

## 复现与证据

通知输入基于 `modules/m2/fixtures/u1_d2_d3_cases.json` 与 `u4_d2_d3_full_correction.json`，所有画像、标题和业务编号均为合成 example。示例演示日为 2026-11-16，实际核验日为 2026-11-10。

```sh
python -B -X utf8 platform/scut-schedule/skills/scut-schedule/scripts/runtime.py timetable --csv modules/m1/examples/timetable.csv --config modules/m1/examples/term-config.json --out work/timetable-plan.json
python -B -X utf8 -m modules.m1.demo
```

更新时从 `modules/m1/examples/d2-d3-workflow.json` 分别取单个对象作为 `--input`，先将保存计划应用到本地表格格式快照，再用 `runtime.py update --existing <最新.csv>` 核对。实际云端写入仍由客户端内置 library 执行，计划中的 `saved_to_cloud=false` 不表示已保存。

原始平台响应、载荷、回读、CSV、截图和本机独立审查结果只保存在忽略的 `.m2-output/c-040-verification/`。仓库不提交平台 ID、个人链接、账号资料或真实学生数据。

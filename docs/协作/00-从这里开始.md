## 每批怎么流转

```text
主管整理任务与共同样例 → 你转发给对应成员
成员做最小可运行版本、自测 → 发分支/PR或ZIP + 交接说明
你把交付链接或文件带回主管会话 → 主管检查业务结果与接口
```

你带回当前会话的最短信息：**“B/C/D + 分支/PR或文件 + 已跑通什么 + 现在卡在哪里”**。主管会读实际文件，不让你代审代码。AI 生成了代码不等于交付；成员要运行至少一个自己的输入并检查结果。

## 提交路径

会 Git 的成员从主分支建立自己的开发分支，例：

```sh
git clone https://github.com/65638/scut-academic-schedule-assistant.git
cd scut-academic-schedule-assistant
git switch -c b/m1-v0
```

C 用 `c/m2-v0`，D 用 `d/m3-v0`。提交后推送自己的分支，在 GitHub 建立发往 `main` 的 Pull Request（PR，即可供审查的改动集合），或直接把分支链接发给你。推送命令中的分支名与自己的分支保持一致：

```sh
git add <本批实际改动的文件>
git commit -m "feat: finish first date sample"
git push -u origin b/m1-v0
```

以上尖括号内容需替换为实际文件；不要求统一提交语言。不熟悉命令就交 ZIP 与 [交接单](交接单.md)，不让 Git 操作阻塞业务工作。

模块脚本可放 `modules/m1/`、`modules/m2/`、`modules/m3/`，样例与相应测试跟随模块。目录是默认归属，不是禁改边界。A 负责把真正运行需要的文件放进 WorkBuddy 专家包，避免各人另建一套存储或复制全部平台代码。
